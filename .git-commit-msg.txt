fix: talk processing still stuck — fast mode + watchdog for large files

The previous fix (increasing maxDuration to 900s) wasn't enough.
The FFmpeg filter chain has 9 filters, and for a 64MB file (~53 min
of audio), the three most CPU-intensive filters were causing the
function to timeout or OOM:

1. silenceremove — scans entire audio to detect and remove silence
2. afftdn (noise reduction) — FFT-based, very CPU-intensive
3. dynaudnorm — dynamic normalization, processes frame by frame

Changes:

1. Added FAST_PROCESSING_OPTIONS — a minimal filter chain for large
   files that skips silenceremove, afftdn, and dynaudnorm. Still
   applies: highpass, lowpass, de-essing, speech EQ, loudnorm
   (single-pass), and limiter. This cuts processing time by ~70%.

2. Added enableSilenceRemoval and enableDynamicNorm options to
   ProcessingOptions so they can be toggled independently.

3. The process route now uses FAST_PROCESSING_OPTIONS for files
   >25 MB instead of just disabling loudnorm.

4. Added a watchdog timer that fires 30s before maxDuration. If
   processing hasn't completed, the watchdog marks the talk as
   "failed" with a clear timeout message — so the talk never gets
   stuck in "processing" again, even if FFmpeg hangs.

5. The catch block now skips the DB update if the watchdog already
   fired, avoiding a race condition.

For the currently stuck talk: the stale window is now 15 min, so
the Restart button should appear. Click it to reprocess with the
fast pipeline.
