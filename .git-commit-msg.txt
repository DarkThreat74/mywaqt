fix: loudness measurement pass still running for large files (root cause)

ROOT CAUSE: The enableLoudnessMeasurement option was being silently
overridden back to true by the options merge order.

The effectiveOptions for large files was:
  { ...FAST_PROCESSING_OPTIONS, ...options, enableSilenceRemoval: false, ... }

FAST_PROCESSING_OPTIONS sets enableLoudnessMeasurement: false.
But ...options inherits from DEFAULT_PROCESSING_OPTIONS which has
enableLoudnessMeasurement: true. The spread ...options comes AFTER
FAST_PROCESSING_OPTIONS, so it overrides enableLoudnessMeasurement
back to true. The explicit overrides at the end included
enableSilenceRemoval, enableNoiseReduction, and enableDynamicNorm
but NOT enableLoudnessMeasurement — so the measurement pass kept
running even in "fast mode".

The measureLoudness function runs a FULL FFmpeg pass over the entire
audio file with the loudnorm filter and pcm_s16le codec. For a 64MB
file (~53 min of audio), this adds 5-10 minutes — pushing total
processing time past the 900s timeout.

FIX:
1. Added enableLoudnessMeasurement: false to the explicit overrides
   in effectiveOptions, AFTER the ...options spread. This guarantees
   the measurement pass is skipped for large files regardless of
   what options contains.

2. Added enableLoudnessMeasurement, enableSilenceRemoval, and
   enableDynamicNorm to the processingOptions() function so they
   can be properly passed through from the client (previously they
   were silently inherited from DEFAULT_PROCESSING_OPTIONS).

With this fix, large file processing is now truly 1 pass:
  - Download (streamed to disk, ~30s for 64MB)
  - FFmpeg processing (6 lightweight filters, ~3-5 min for 53min audio)
  - Upload (~15s for ~4MB processed file)
  - Total: ~4-6 min (well within 900s timeout)
